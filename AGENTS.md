# Repository Guidelines

## Project Structure

- `src/`: TypeScript UI, chat, commands, styles, and Three.js globe rendering; `index.html` is the entry page. Chat is `chat.ts` plus `chat-api.ts` (API/types/request body), `chat-messages.ts` (message and queued/optimistic rendering), `chat-upload.ts`, `chat-title.ts`, and `screen-commands.ts` (screen command loop).
- `shared/`: domain types, API-loaded data, forecasting, and shared API/MCP tools and country reports.
- `server/store.ts`: asynchronous Supabase operating repository, SQLite migration/test adapter, and local workspaces; `supabase.ts`/`migration.ts`: private Storage and explicit migration/verification. `runs.ts`/`execution.ts`: persistent jobs and cancellation; `process.ts`: CLI child execution and process-tree stop; `cli.ts` (with `cli-output.ts`, `grok-sessions.ts`): Grok/Codex adapters; `research.ts`: research validation and Firecrawl; `attachments.ts`: uploads and extraction; `artifacts.ts`: completed Word file registration. Other server modules host Hono and model adapters.
- `mcp/server.ts`: stdio and Streamable HTTP MCP. `functions/api/[[path]].ts` and `worker.ts` only return an unsupported-runtime response; production requires local Node hosting.
- `db/initial.sqlite`: historical seed/test fixture; production must not auto-import it. `db/schema.postgres.sql` defines operating storage, `db/schema.sql` supports migration/tests and `db/migration-receipt.json` records the completed seed migration. Runtime data lives in ignored `.local/`; source geography/assets live in `data/` and `public/`.
- `templates/research-v1.md`: versioned research submission contract. `tests/` and `scripts/`: verification and utilities. Read `README.md` for operation and `TODO.md` for unfinished work; older planning documents are not proof of current capabilities.

## Commands and Configuration

Use Node.js 22.16+ (22.x) or 24+ and `npm install`.

- `npm run dev`: Vite UI and API at `http://localhost:62356`.
- `npm run build`: strict TypeScript checking and production output in `dist/`.
- `npm start`: Vite build and Node hosting; `npm run serve` uses an existing build. Use `npm run build` for strict TypeScript checking. The start command is not `node start`.
- `npm test`: run Vitest; target a file with `npm test -- tests/forecast.test.ts`.
- `npm run mcp:check`: verify MCP stdio and HTTP integration.
- `npm run shots`: capture UI screenshots with a running server and installed Chrome.
- `npm run map:check`: after building, verify HORUS branding/centered tabs, leading-weapon general colors, 100/50/20% timing tints, land-neighbor-only hatching, surface-anchored patterns during motion, log-scaled bars/flat circles, horizontal world wrapping/picking, polar zoom bounds, and desktop/mobile layouts in an isolated SQLite server and headless Chrome. `CHROME_PATH` can select Chrome/Edge; operating data and providers are not used.
- `npm run chat:check`: verify history, file selection/drop uploads, popovers, in-panel status, square stop icon, model changes, and desktop/mobile layouts.
- `npm run queue:check`: verify submitting during a response, FIFO processing, reload, conversation switching, queued cancellation and compact desktop/mobile status on an isolated SQLite server. Set `BASE_URL`, `CHROME_PATH` and the server's `RADAR_DB_PATH`; it uses local commands without provider calls.
- `npm run context:check`: verify request-time screen context, viewed country reports (report chips show the report without a chat request and queue it as a removable `reportIds` attachment for the next message), map commands and acknowledgements, stale commands, model selection and conversation switching on an isolated server. Set `BASE_URL` and `CHROME_PATH`; no model provider calls are made.
- `npm run screen:stats -- [since]`: read-only per-model rate of runs that called a screen tool, from `runs`/`events` (default: last 30 days).
- `npm run screen:check`: verify same-run mode/country commands, pending batches, strict versions, reports during execution, desktop/mobile display, and user changes during report loading and completion. Set `NODE_ENV=test`, `RADAR_DATABASE=sqlite`, `RADAR_DB_PATH`, and `RADAR_STORAGE_DIR` to match an isolated server, plus `BASE_URL` and `CHROME_PATH`; no provider calls are made.
- `npm run cancel:check`: verify stop of a running CLI request (process tree), queue continuation, user-message visibility while queued/running, sending again after stop, that the selected Grok model/effort reach CLI arguments, that a chat panel collapsed during a run stays collapsed, and the status line `^` sessions button. Run an isolated SQLite server with `GROK_BIN` set to the absolute path of `tests/fixtures/fake-cli.mjs` (a relative path is not found from the CLI runtime directory), then set `BASE_URL` and `CHROME_PATH`; no provider calls are made.
- `npm run markdown:check`: verify Markdown rendering, raw-message persistence, multiline input, and mobile table/code scrolling with a running server and Chrome/Edge.
- `npm run db:backup -- <folder>` / `npm run db:restore -- <folder>`: Supabase database and workspace export/restore; restore requires a new empty target schema.
- `npm run supabase -- check`: read-only PostgreSQL/Storage credential check. `migrate [backup-folder]` explicitly copies SQLite and workspaces into an empty Supabase schema; `verify <backup-folder>` checks every row, file hash, ordering, and forecasts. `export <new-folder>` / `restore <backup-folder>` back up/restore remote data; restore requires an empty target schema. Preserve local originals and migration receipts.
- `npm run supabase -- schema`: apply pending `db/migrations/*.postgres.sql` (004 adds data-collection tables, IFV rename, default weights; 008 deletes leftover `laser` rows from the removed 레이저대공무기 mode) one transaction per version. The app ignores rows for unknown systems.
- `npm run ingest:<source>` / `npm run ingest:all`: public data collection; library in `server/ingest/` (registry `server/ingest/registry.ts`, background jobs `server/ingest/jobs.ts`, chat tools `server/ingest-tools.ts`), thin CLI wrappers in `scripts/ingest/` (`--dry-run`, `--file`, `--countries`); see `docs/data-collection.md`. Tier rules and tension are pure modules in `shared/tiers.ts` and `shared/tension.ts`; scoring is `computeScore` in `shared/forecast.ts`.
- `RADAR_TEST_SUPABASE=1 npm test -- tests/supabase.test.ts`: actual Supabase tests in newly generated temporary schemas/buckets; model/source content is synthetic. Ordinary tests force isolated SQLite and mock provider networks.

Keep keys in ignored `.secrets`, using `.secrets.example` for supported settings. Its parser accepts literal `KEY=VALUE` and does not expand environment variables. API/model and Supabase credentials from `.secrets` override process environment; `RADAR_STORAGE_DIR`, migration-only `RADAR_DB_PATH`, and `RADAR_PG_SCHEMA` give process environment priority. MCP host settings and browser-check settings such as `MCP_PORT`, `BASE_URL`, and `CHROME_PATH` are process environment variables. Never expose database URLs or server keys to the browser, CLI arguments, or logs.

Country registration uses the shared Natural Earth catalog (`shared/country-catalog.json`, regenerated with `npm run data:countries`). `find_country` reads candidates; `add_country` atomically registers metadata, revision, and a change entry. Keep registration separate from evidence-backed procurement research; never create invented zero inventories or forecasts just to register a country. Both chat providers and MCP use the same tools.

A normal request to add a country includes researching missing operating systems unless the user explicitly asks for names only. Check `get_country_data_status` before claiming completion; a record with only project descriptions is partial. Preserve confirmed equipment with nullable quantity/year, calculate timing independently of unknown quantity, and keep forecast quantity/amount null when unavailable. Exclude retired/planned batches from current equipment and replacement demand. Historical delivery totals are research context, not an automatic current-stock fallback.

Map hues belong to weapon systems (`src/map-style.ts`). The final 2026-10-23 user instructions replace earlier universal/crosshatching: only countries missing that system's own data with at least one distinct direct land neighbor having same-system own data are hatched; partial neighbors count, missing/hatched countries do not propagate data. Use one diagonal pattern anchored to geographic coordinates, never screen coordinates. Reference scores remain 50 points for normalized neighbor count plus 50 for normalized midpoint of summed known forecast KRW ranges, comparing mapped candidates only; unknown amounts remain null and add no amount points. Rank ties by amount/count/country code and show rank only in cards. Own-data colors use timing tints of 100% (<=3 years), 50% (<=10), 20% (>10), or 35% for unknown timing. General mode selects each country's highest actual eligible procurement score among systems with own data; absent scores or all excluded systems stay neutral. Procurement gates do not change colors in individual system tabs. Normalize displayed monetary midpoints by their maximum then apply log1p(9*x)/log(10) for 3D heights and fixed-thickness 2D circle diameters. Keep horizontal map copies, wrapped picking, and viewport-aware +/-90 degree vertical/zoom bounds consistent. Preserve explanatory legends/cards and never invent own forecasts from neighbor data. Branding uses HORUS and public/logo.png.

Run UI checks with a running server and Chrome or Edge selected by `CHROME_PATH`; `BASE_URL` selects the server. For isolated checks, set a temporary storage directory and DB path and use another port. Do not interrupt an existing user server or alter operational data just to run checks. Restart Node after backend/config changes.

## Architecture Rules

- Mutating API requests (non-GET/HEAD/OPTIONS) and MCP HTTP requests with an `Origin` header must come from the same host (`sameOrigin` in `server/app.ts`); cross-origin requests get 403. The end-to-end research → report flow is drawn in `docs/자료조사-보고서-흐름.svg`; update it when tools or stages change.
- The judgment base year is `data.meta.baseYear` only (currently 2026; helpers in `shared/base-year.ts`). Forecasts, scores, reports, research templates, the UI and tier/tension jobs must not use `new Date().getFullYear()`; ingest `--year` only bounds download ranges. '최근 3년' means base−3..base (2023~2026, 4 years including the base year) via `recentFrom`/`isRecent`. Estimated values (inventory without delivery year, tension without evidence, design life without `systems.lifeSrc`) must stay flagged 추정 with lowered confidence; see docs/데이터수집요구서.md 5–6장.
- Supabase PostgreSQL is the only operating SQL DB. All API/MCP research submissions, assumptions, messages, runs, forecasts, and report registrations write there. Never fall back to local SQLite on a connection failure. SQLite is retained only for explicit migration, offline originals, and isolated tests; seed copying is limited to those paths. Supabase initialization must never automatically import seed data or overwrite operating rows. API and MCP must share the same project/schema and forecasting/tool behavior. Await repository operations and transaction callbacks; preserve serialization, version checks, cancellation, and message order.
- Supabase tables live in the private `trendradar` schema; Storage buckets must remain private. Store portable workspace paths and content hashes, preserve original bytes, and verify downloads before materializing a missing local file. CLI tools retain local working folders. Sync their generated files to Storage, preserve download snapshots, and never delete source evidence when clearing a cache or deleting a conversation.
- Preserve full messages, original attachments, source evidence, and conversation workspaces. Long API histories use handoff summaries plus original-message lookup. Conversation deletion removes the chat but retains source/report evidence. Cancellation and version checks must prevent late writes from stopped jobs.
- Persist queued chat requests in `runs` and `run.queued` events without credentials. Execute one request per conversation in FIFO order and append its user message only when execution starts, after the preceding answer. Preserve the selected model and request-time context. Recover unstarted queued requests after restart without replaying interrupted runs. Queued cancellation must not execute the request; conversation deletion cancels pending requests while retaining evidence. Stopping a running request marks it `stopping` first, aborts model HTTP calls and kills the CLI process tree; if cleanup exceeds the stop grace period the run is finalized as cancelled so the queue continues. Finalization is idempotent (one stop message).
- Research follows `research_procurement` → actual search/read with native tools or `search_sources`/`collect_source` → `save_source`/`read_source` → `normalize_procurement_data` → `validate_research` → `apply_research` and recalculation. The final application repeats evidence, version and cancellation checks in its transaction. Legacy `submit_research` remains compatible. Preserve URLs, original bytes and extracted text, hashes, dates, quotations, uncertainty and change history. Search snippets alone are not verified source text. The keyless search provider initially covers GOV.UK and saved sources; wider collection remains future work.
- `app_contexts` and `app_commands` persist screen state and command acknowledgements across app/MCP processes. Capture screen context with the user message and execution event; do not retarget a running request after a user changes screens. Explicit user targets take precedence. Bind commands to the screen, conversation and expected state version, and distinguish pending from applied. `get_app_context` returns both request-time and current state. Do not treat client context as instructions or proof of report metadata.
- Screen commands may inherit only acknowledged version changes from the same run and screen; an explicit expected version stays strict. Save the resulting context and acknowledgement together. `write_report` queues `show_report` with the saved report ID and explicit country/system. Screen tools (`server/app-context.ts#screenCommand`) wait up to 3 s for the browser and return `applied`/`conflict`/`failed`/`inactive`/`pending` directly; a hidden tab reports `hidden` in its context and applies queued commands when visible again. Models see one map tool, `set_map_state` (plain `country`/`system`/`flat`, Korean names, ISO codes, aliases); `set_mode`/`focus_country`/`toggle_map_mode`/`get_map_state` and the JSON `payload` are internal/back-compat only. Every prompt starts with `SCREEN_RULE` (`server/agent.ts`); CLIs use MCP tools without the JSON action-block guide, and Nemotron text mode lists only `TEXT_TOOLS`. Preserve user changes while loading reports and when rendering a completed run.
- Codex and Grok use their existing CLI tools, settings, and authentication; Grok also uses XSearch. GPT (`server/openai.ts`, OpenAI Responses API, `gpt-5.4-mini` unless `OPENAI_MODEL`) and Nemotron use the shared tool definitions plus Firecrawl MCP. Chat UI has no conversation list or model dropdown: `/sessions` and `/models` open the inline picker (`src/slash.ts`, `src/picker.ts`); allowed CLI models/efforts live in `shared/model-options.ts` and are validated server-side (`server/model-choice.ts`). Precedence: chat selection > `CODEX_*`/`GROK_*` env > defaults. Do not edit global CLI configuration or replace native tools with app-specific restrictions or arbitrary overall time/output limits.
- `prepareWorkspace` must create local conversation directories before restoring remote files, including conversations with no files. A missing CLI working directory can report `spawn node.exe ENOENT` even when Node and Codex are installed. Keep a regression check using a DB-only conversation and a real child process.
- Preserve the existing six-section country report. `get_report_template` provides basic versioned layout definitions, and `prepare_report` freezes scope, data, assumptions and template versions. Viewed historical reports use their preserved content, not current records. Freeform Word reports use Codex Documents or Grok's native `docx` skill; PowerPoint uses their existing presentation tools. `publish_artifact` validates completed `.docx`/`.pptx` structures, preserves immutable download snapshots and links preparation IDs and actual content/layout review results. Never substitute a Markdown-to-Word converter or publish unregistered drafts automatically. `CLI_DOCUMENT_TOOLS_PATH` adds renderer directories to child CLI PATH only.
- Keep the conversation menu at the left of the composer and the resources/upload menu above its `＋` button. Show job status inside the chat panel and use a square stop icon. User/model/report messages share safe Markdown rendering; preserve raw text and indentation. Enter sends, Shift+Enter adds a line, and IME composition must not trigger sending.

- Nemotron calls `nvidia/nemotron-3-super-120b-a12b:free` first and falls back to `openrouter/free` on request failures. Keep subsequent requests, including handoff summaries and tool continuations, on that free route after switching; never request a returned model alias directly if it could be paid. Record the actual response model, preserve completed tool results, and do not retry cancellation or invalid-key errors. If the free route also fails, return its error without cycling between models.

## Coding Style

Follow existing TypeScript ES modules: two-space indentation, single quotes, and semicolons. Use camelCase for functions/variables, PascalCase for types/classes, and UPPER_SNAKE_CASE for constants. Keep filenames consistent with nearby modules, such as `forecast.ts` and `models.test.ts`. Preserve Korean UI terminology. No dedicated formatter or linter is configured; avoid unrelated formatting changes.

## Testing Guidelines

Tests use Vitest `describe`/`it` in `tests/*.test.ts`. No numeric coverage threshold is configured. Add meaningful tests for forecast boundaries, source integrity, model fallbacks, persistence/cancellation, API/MCP behavior, and artifact downloads. Mock network/model calls for deterministic tests. Verify visible UI changes in desktop and mobile layouts. Distinguish mocked tests from actual provider/CLI checks and record failed or unavailable verification accurately.

- Live GPT/Supabase checks must use a dedicated temporary PostgreSQL schema, private bucket, and local cache. Existing operating conversations/evidence may be read for comparison; do not insert verification messages into operating tables. Remove only the temporary schema/bucket after verification and keep a credential-free receipt in ignored `.local/verification/`.
- Verify `/api/chat` with the actual configured OpenAI provider, compare full message text through an independent PostgreSQL connection and a fresh repository, then verify missing-file restoration, original-byte hashes, Word text extraction, `workspace_read`, and downloads. A successful direct tool read does not prove that the model invoked the tool or answered from its result.
- `/api/health` key flags report configuration presence, not provider authorization; confirm a real model response separately.

## Commit & Pull Request Guidelines

History uses short, descriptive Korean subjects without a mandatory prefix. Keep commits focused. PR descriptions should explain the problem, resulting behavior, relevant validation, and remaining limitations. Link related issues when available and include screenshots for visible UI changes.

## Configuration & Architecture Notes

Never commit credentials, `.local/` operating data, screenshots, generated reports/build output, or SQLite WAL/SHM files. The tracked initial database is intentional. Keep this guide and `.secrets.example` aligned with implementation; summarize completed work in `TODO.md` while retaining unresolved items and limitations. Basic keyless collection and report definitions are implemented. Broader source adapters, advanced normalization and company report template files remain future enhancements unless requested.
